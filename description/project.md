# 燃动现象管理端项目说明

## 1. 文档目的

本文档用于说明燃动现象的项目定位、核心玩法、管理端范围和关键业务规则，帮助开发人员与智能体快速建立统一的业务认知。

项目已进入功能收口阶段。本文档只描述已经明确且相对稳定的核心业务，不展开页面视觉、接口字段和数据库实现细节。具体实现状态参见对应功能文档，数据结构参见 `description/db/`，接口行为以后端契约为准。

## 2. 项目定位

燃动现象是一款面向企业员工的运动赛季应用，包含员工使用的客户端和管理员使用的管理端。

- 员工以赛季为周期参加运动挑战，通过上传运动凭证推进项目进度。
- 系统和管理员对运动凭证进行初审、终审，并据此计算有效进度。
- 赛季结束后，系统根据挑战完成情况和最终审核结果统一结算积分。
- 用户积分跨赛季累计，可以在积分商城兑换商品。
- 本仓库负责管理端前端，主要用于配置赛季和挑战、审核凭证及管理积分商城。

管理端通过单一管理员密钥换取短期访问令牌。令牌用于接口准入，不构成完整的管理员账号、角色或细粒度权限体系。

## 3. 业务角色

### 企业员工

通过客户端参与赛季、选择运动项目和挑战等级、上传运动凭证、查看排行榜，并使用积分兑换商品。

### 管理员

通过管理端维护赛季、运动项目、挑战等级和规则，对运动凭证进行终审，并管理商城商品、兑换和发放情况。

### 系统与大模型

后端负责报名校验、数据一致性、进度计算、排行榜刷新和积分结算。大模型负责凭证初审，并给出单条凭证的原始进度增量。

## 4. 核心业务流程

```text
管理员配置赛季、项目、挑战等级和规则
    ↓
用户在报名期内选择指定数量的项目
    ↓
用户为整个赛季选择一个统一挑战等级并正式参与
    ↓
用户上传运动凭证，大模型执行初审
    ↓
初审通过后增加项目进度并进入排行榜统计
    ↓
管理员持续进行人工终审
    ↓
赛季结束后统一结算积分
    ↓
用户使用跨赛季累计积分兑换商品
```

## 5. 客户端核心玩法

### 5.1 赛季参与

- 平台同一时间以一个当前赛季作为主要参与对象，并且只允许一个赛季处于进行中状态。
- 赛季包含开始日期、结束日期、必须选择的项目数量，以及可参与的挑战等级和对应规则。
- 用户只能在允许的报名时间内参与赛季。赛季开放后可以提前报名；赛季开始后，只能在规定的前若干天内报名。
- 用户必须先选择赛季要求数量的运动项目，再为整个赛季选择一个统一的挑战等级。
- 必选项目数量由赛季配置决定，不固定为三个。
- 同一用户在一个赛季内选择的所有项目共用同一个挑战等级。
- 项目和挑战等级锁定后，原则上不能随意更换。

### 5.2 运动项目、等级与规则

- 平台可以配置日常步数、跑步或快走、健身、球类活动、户外运动和减重挑战等项目。
- 挑战等级可以对应不同的目标和赛季奖励积分；等级越高，目标和奖励积分通常越高。
- 项目规则可以包含累计次数、累计达标天数、累计距离、累计时长、单次距离、配速、爬升或减重目标等指标。
- 用户确定项目和统一挑战等级后，系统根据“项目 + 等级”读取对应挑战规则。
- 按当前数据库设计，项目规则是平台通用配置，不随赛季复制。如果后续需要同一项目在不同赛季使用不同规则，应单独调整后端和数据模型。

### 5.3 凭证上传与重传

- 用户只能为当前赛季中已经锁定的项目上传凭证。
- 每条凭证包含实际运动日期、凭证图片、运动备注和凭证类型。
- 运动日期必须处于赛季起止日期内，且不能晚于当天。
- 同一用户、同一项目、同一个运动日期，只允许存在一条有效凭证，不同凭证类型不能绕过该限制。
- 普通上传默认选择当天，补传可以选择赛季内已经过去的日期，两者遵循同一套校验规则。
- 对已有日期再次上传视为重传。重传会清除原审核结果和审核意见、撤销原进度贡献，并让新图片和备注重新进入待初审状态。

### 5.4 初审、终审与项目进度

凭证审核状态包括：

| 状态 | 含义 |
| --- | --- |
| `pending` | 待初审 |
| `preliminary_approved` | 初审通过 |
| `preliminary_rejected` | 初审失败 |
| `approved` | 终审通过 |
| `rejected` | 终审拒绝 |

- 初审判断单条运动记录是否满足单次要求，不使用“累计次数不足”“累计天数不足”等赛季整体条件拒绝一条本身有效的凭证。
- 初审失败的凭证不增加项目进度，用户可以重传后重新审核。
- 初审通过后，大模型给出原始进度增量 `progress_delta`，系统根据项目剩余空间计算实际生效增量 `increase`。
- 项目进度范围为 `0～100%`，等于当前有效通过凭证的 `increase` 总和，不得超过 `100%`。
- `progress_delta` 保留凭证原本能够贡献的进度，`increase` 记录该凭证当前实际占用的进度。
- 管理员可以在赛季期间持续进行终审。终审通过后保留进度贡献；终审拒绝后，凭证不再贡献进度，也不再计入后续排行榜统计。
- 凭证因重传或终审拒绝释放进度空间后，系统会尝试使用同项目下其他有效通过凭证尚未生效的 `progress_delta` 回补进度。

进度撤销、重新分配和回补必须由后端保证事务一致性，管理端只负责展示结果和发起明确的审核操作。

### 5.5 减重挑战

- 月初记录用于建立初始体重和 BMI 基线，本身不推进项目进度。
- 月末记录必须存在有效的月初基线；达到目标后，减重项目可以直接完成。
- BMI 根据用户身高和凭证中的体重信息计算，不作为所有凭证的通用字段保存。
- 排行榜中月初基线不计为有效打卡，月末通过记录最多计一次。

### 5.6 排行榜、赛季结算与积分

- 排行榜以当前赛季的有效通过凭证数量作为主要统计依据。
- 初审通过和终审通过的有效凭证可以参与统计；待初审、初审失败、终审拒绝、已被重传替换或已作废的凭证不计入统计。
- 排行榜展示用户、部门、挑战等级和有效打卡次数，数据由后端定期刷新，不保证上传后立即变化。
- 赛季期间主要推进项目进度并完成审核，不按单条凭证即时发放积分。
- 赛季结束后，根据用户挑战等级、各项目完成进度、凭证最终审核结果和等级奖励统一结算积分。
- 用户积分跨赛季累计，每次增加或扣减均通过积分流水记录。

### 5.7 积分商城

- 用户可以使用全局累计积分兑换商品，商品具有对应的兑换积分要求。
- 兑换成功后扣减用户积分，并生成积分变动流水。
- 商品与赛季脱钩，可以由管理员新增、修改、上架或下架。
- 历史兑换应保留兑换时实际消耗的积分，避免商品后续调价影响历史数据。

## 6. 管理端功能范围

当前管理端围绕数据看板、平台配置和用户事务三个页面组织下列业务能力。

进入这些模块前，前端必须先通过管理员密钥登录接口获得有效访问令牌，并在受保护请求中携带标准 Bearer 请求头。刷新页面时通过会话接口重新确认缓存令牌；令牌失效后返回前端登录视图。

### 6.0 数据看板

- 获取当前激活赛季的名称、起止日期、必选项目数量和正式参赛人员。
- 当前赛季接口已经按项目数量达标且挑战等级已锁定的口径筛选正式参赛人员，前端不重复推导资格。
- 根据正式参赛人员的锁定等级汇总各等级报名人数，并保持等级总人数与正式参赛总人数一致。
- 管理员点击等级统计后，按该等级的用户 ID 补充查询姓名和部门，再通过受保护的管理端头像接口分批加载头像，用于展示真实报名人员详情。
- 独立获取全部项目并建立共享目录，筛选其中 `status = 1` 的项目，再以当前赛季每个 `season_user_id` 和每个可见项目 ID 查询有效项目记录，按项目聚合实际报名人数和完成进度。
- 项目接口返回的 `user_id` 与已取得的正式参赛人员资料对应；姓名、部门和头像资料可以在多个项目名单中复用，挑战等级沿用当前赛季锁定等级。
- 没有激活赛季、激活赛季冲突或接口异常时展示明确空状态，不沿用旧赛季占位数据。

### 6.1 赛季管理

- 查看赛季列表和赛季状态。
- 新增赛季。
- 查看和更换全局活动海报；上传前由浏览器压缩并转换为 WebP。
- 新建时校验赛季日期和必须选择的项目数量，避免与既有赛季重叠。
- 当前不提供已有赛季编辑、删除或手动状态变更。

报名开放时间和“赛季开始后允许报名的天数”已经是业务规则，但现有数据库文档尚未定义对应配置字段。管理端应以后端实际接口为准，不自行构造字段。

### 6.2 运动项目与挑战等级管理

- 新增运动项目，并在创建时提交各等级规则和凭证上传配置。
- 修改运动项目可见状态，以及现有“项目 + 等级”的规则值。
- 新增挑战等级并维护等级奖励积分。
- 当前不提供已有项目资料编辑、规则指标结构调整、独立上传配置维护或挑战等级状态维护。
- 被历史数据引用的项目、等级和规则优先停用，不直接物理删除。

### 6.3 运动记录审核

- 按当前赛季每名正式参赛人员的 `season_user_id` 获取初审通过且仍有效的待终审凭证，并按运动日期、上传时间和凭证 ID 全局倒序展示。
- 打开待终审凭证时，使用该记录的项目 ID 与参赛人员锁定的等级 ID 获取对应规则指标，作为管理员审核要求。
- 查看用户、运动日期、运动备注、运动图片和初审意见。
- 对初审通过的凭证执行终审通过或终审拒绝，并按需填写审核意见。
- 清楚展示终审操作会影响项目进度和排行榜资格；实际撤销与回补由后端处理。
- 审核请求不自动重试，只有服务端确认成功后才移除记录并同步相关项目进度。

### 6.4 积分商城与兑换管理

- 查看、新增和修改商品信息，包括名称、说明、所需积分、图片和上下架状态。
- 查看真实待发放奖品，并对发放或拒绝操作执行二次确认。
- 用户事务中的“积分与兑换”智能查询已通过 `rewards` 业务域接入后端查询智能体；结果字段和可查询范围以后端白名单为准，不由前端根据数据库文档补造。

现有数据库文档只定义了商品和积分流水，尚未提供独立的兑换订单及发放状态模型。兑换记录、收件信息和发放状态的具体字段，应以后端接口或后续数据库文档为准。

### 6.5 赛季结算

- 获取唯一 `status = 2` 的结算中赛季，以及满足正式参赛条件的全部 `season_user_id`。
- 批量加载结算参与者资料、项目进度、最终积分和积分发放状态，并把用户信息写入工作台共享目录。
- 查看结算赛季待终审凭证，复用参与者、项目和规则目录完成终审通过或拒绝。
- 对已完成定分且尚未发放的用户执行二次确认后发放积分；页面只使用服务端返回结果更新状态。
- 支持输入完整赛季确认短语后执行一键结算，由后端事务统一拒绝未完成审核的凭证、重算进度、定分、发放积分并结束赛季。

### 6.6 用户意见

- 查看后端返回的可见用户意见，并通过受保护头像接口补齐提交用户头像。
- 对单条意见执行二次确认后标记为已优化或拒绝，仅在服务端成功后从待办中移除。
- 当前接口没有已读状态、独立详情或回复能力，页面不自行推断“新意见”口径。

## 7. 仓库职责边界

- 员工客户端的报名、项目选择、凭证上传和商城兑换页面。
- 大模型初审算法及提示词实现。
- 排行榜定时任务、进度回补和赛季积分结算的后端实现。
- 数据库结构调整和后端接口设计。
- 完整的管理员账号、角色和权限体系；如后端已有权限能力，管理端按接口接入。

| 业务概念 | 数据实体 |

| 赛季 | `season` |

## 9. 待统一和待确认事项

以下事项不阻塞当前管理端使用，但在相关功能继续开发前需要确认：

1. 赛季报名开放时间及赛季开始后可报名天数的接口和数据字段。
2. 兑换时积分快照、收件信息、物流与撤销发放的数据模型和接口；待发放查询与确认发放口径已经由管理端接口明确。
3. `description/db/project-rule.md` 中“选择 3 个运动项目”的旧背景描述，应统一为由 `season.required_project_count` 决定。
