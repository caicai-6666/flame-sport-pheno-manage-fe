# 挑战配置管理

挑战配置管理用于维护平台统一的挑战等级、运动项目，以及“项目 + 等级”对应的挑战规则。当前阶段已接入挑战等级列表、创建与奖励积分修改，以及运动项目目录、创建、规则修改和可见状态修改。

---

## 当前页面范围

管理员在平台配置中选择“挑战等级”后，右侧内容区以卡片网格展示全部等级。每张卡片只承载两项核心信息：

- 等级名称。
- 达成该等级挑战后的奖励积分。

等级正面采用整张深色液态徽章卡，不再使用彩色上半区加白色奖励底栏。青铜、白银和黄金按名称匹配铜、银、金材质；其他自定义等级按 ID 稳定分配蓝宝石、紫晶或翡翠主题。PixiJS 围绕中央奖章绘制多层闭合液态等高线，默认持续轻微呼吸、漂移和反向旋转，悬停时切换到更快、更强的动态档位；该结构不复用赛季卡片的流带、液滴和位移过滤器。

等级数据来自 `GET /project-level/list`，包含等级 ID、名称和奖励积分。接口返回全部等级，并已按 `reward ASC, id ASC` 排序；前端保留该顺序。卡片不展示项目规则，因为规则属于“运动项目 + 挑战等级”的组合配置，不是等级自身字段。

列表在挑战等级子页首次选中并挂载时请求；平台配置通过 `KeepAlive` 保留子页实例，后续切换回来不会重复请求。加载期间展示同步状态，空数组展示空状态，异常时展示安全提示和重试入口。

点击任一等级卡片后，卡片原位翻转到奖励积分编辑表单。管理员输入 `0～4294967295` 的整数后，第一次保存会让按钮平滑变换为 3 秒确认状态，第二次确认才调用 `PATCH /project-level/{level_id}/reward`。服务端成功后使用响应结果更新卡片并恢复 `reward ASC, id ASC` 排序；失败则保留草稿与后端安全提示。

积分修改是否允许完全由后端激活赛季配置窗口守卫判断。前端不读取 `ACTIVE_SEASON_CONFIG_EDIT_WINDOW_HOURS`，遇到 `409 Conflict` 时展示后端 `detail`，且不自动重试写操作。

等级网格第一位固定展示“新建等级”加号卡片。点击后，新建表单从内容容器底部升起，管理员需要填写唯一的等级名称和 `0～4294967295` 的整数奖励。第一次点击创建进入 3 秒二次确认，第二次确认后才提交；服务端返回并通过校验后，新等级按奖励积分、主键升序加入列表。

服务端创建等级时会在同一事务中为所有项目建立相同指标名称的规则骨架，要求值暂存为 JSON `null`。创建成功后，等级页通过平台配置通知运动项目页废弃旧等级快照；运动项目页仍不批量预取规则，而是在下一次打开具体项目时加载新等级组合，并把空要求值展示为“待设置”。

> [!NOTE]
> 当前列表查询、新增和奖励积分修改均使用真实接口。

### 运动项目

管理员选择“运动项目”后，右侧内容区以卡片展示走路、跑步、羽毛球、篮球、爬山和健身。

已有项目使用深色星河卡片：PixiJS 绘制紫、粉、蓝、青、金五层弯曲星云带、局部星云核心、不同深度的彩色星尘和少量带拖尾星点。星河在默认状态下缓慢迁移，悬停或键盘聚焦时增强流速、视差、星云宽度和拖尾长度；每个项目按稳定 ID 生成不同的轨道与配色顺序。项目放大翻转期间沿用同一视觉，新建项目入口不渲染星河。透明黑色项目图标在星河正面转为冷调亮色轮廓，在规则背面转为与项目主色一致的深色轮廓。不可见卡片、详情背面和新建表单打开期间暂停渲染，系统启用减少动态效果时只保留静态星河画面。

点击任一项目时，卡片会从原位置向中央放大并同步翻转。背面按青铜、白银、黄金划分等级区域，每个等级下的规则统一使用以下形式：

```text
每日步数 — 6000 步
达标天数 — 累计 18 天
```

项目规则来自“项目 + 等级”的唯一组合。不同项目可以使用不同数量和类型的指标，详情区域应按 `rule_content` 数组顺序展示，不将指标写死为固定字段。

每个等级规则区域采用单面卡片，依次展示 `sub_desc` 挑战副描述、`rule_content` 指标和 `rule_note` 规则备注；三部分来自同一次按需规则请求，并共用 `project_id + level_id` 缓存。空副描述或备注使用占位提示，不会产生额外请求。

项目网格第一位提供“新建运动项目”入口。创建表单分为三个步骤：

1. 按 `project` 填写项目名称、说明和图标；图标仅接受不超过 5 MB 的 WebP，并在前端清除边缘连通的近似纯色背景、重新编码并压缩至 60 KB 以内，同时保留透明通道；新项目固定以隐藏状态创建，不在表单中选择状态。
2. 打开表单前按需请求 `/project-level/list`（已有快照时复用），并为返回的每个 `project_level` 配置 `project_rule`；指标名称和每个等级的全部指标值必填，规则固定为可见且不提供隐藏控件，副描述与备注保持选填。
3. 按 `project_upload_config` 配置凭证；顶部组合菜单只提供普通凭证和“月初 + 月末记录”两个选项，选择后自动展示对应的一张或两张只读类型配置卡，不能手工混用或拆散月度组合。配置固定启用，管理员继续填写上传提示、备注示例和排序。

表单提交结果按事务写入职责封装为 `project`、`project_rules` 和 `project_upload_configs` 三组 JSON。项目主键在创建前不存在，两个子列表不提交虚构的 `project_id`，由后端创建事务补齐关联。

公共指标名称只录入一次，不同等级分别填写要求值。提交时再按等级拆分为各自的 `rule_content`，避免同一项目的等级规则出现指标名称不一致。

项目卡片背面提供以下管理动作：

- **修订**：在项目详情上方打开独立修订卡，不改变原等级网格布局；左右配置面板保持等高，指标过多时右侧指标列表独立滚动。可修改 `sub_desc`、`rule_note` 和既有 `rule_content[].value`。指标标签、顺序和值类型不可变；编辑器根据原值类型自动选择控件，不提供类型选择。原值为 `null` 时允许首次填写文本值，留空仍提交 `null`。
- **隐藏项目**：调用真实状态接口将项目调整为停用，但继续在管理端以弱化卡片展示；成功后同步数据看板可见项目和赛季容量。
- **恢复显示**：调用真实状态接口将已隐藏项目重新调整为启用。
项目管理不提供删除入口。已被历史数据引用或暂时不再开放的项目统一使用隐藏状态退出普通可选项目口径。

> [!NOTE]
项目创建已经接入真实 multipart 接口，三段 JSON 与 WebP 文件由后端在同一事务写入并上传图标；创建按钮使用 3 秒二次确认。单等级规则配置与项目状态也已接入真实 `PATCH` 接口。

## 数据口径

等级名称和奖励积分分别对应 `project_level.name` 与 `project_level.reward`。奖励积分用于赛季结束后的统一结算，不在用户上传单条运动凭证时即时发放。

等级状态对应 `project_level.status`，但当前卡片和列表接口未提供状态展示与维护交互。是否显示停用等级及其弱化方式仍需结合后端契约和产品交互确认。

项目在各等级下的完成条件来自 `project_rule`。平台配置不会提前请求全部组合：只有打开项目卡片时才取得挑战等级列表，并以最多 5 个并发请求获取该项目各等级规则；组合结果按 `project_id + level_id` 缓存。前端不得把某一项目的规则误认为等级本身的通用条件。

待终审详情与配置页面共享按 `project_id + level_id` 建立的规则目录。审核场景只读取消费规则；配置页面通过独立修改接口提交既有指标值，并在成功后更新共享目录。

## 当前限制

- 挑战等级列表已接入真实查询接口。
- 挑战等级新增已接入真实创建接口，名称冲突由服务端唯一键最终约束。
- 奖励积分编辑已经接入真实修改接口，并由后端统一执行激活赛季配置窗口校验。
- 运动项目已接入项目创建、单项目单等级规则修改及项目可见状态修改；不提供项目删除入口，已有项目资料修改、指标结构调整及独立上传配置维护仍待后续设计。
