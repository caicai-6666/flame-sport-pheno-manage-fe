# 用户事务页面

用户事务页面用于集中处理与具体用户行为和结果相关的管理工作。当前阶段已建立页面入口、三类业务导航骨架，以及接入真实接口的**赛季结算列表**、**运动记录智能查询**和**积分与兑换智能查询**。

---

## 页面进入方式

管理员点击顶部“用户事务”后：

1. 顶部胶囊导航中的白色滑块平滑移动到第三项。
2. 当前页面沿水平方向向左离开可视区域。
3. 用户事务页面从右侧进入。
4. 左侧三个分类条目依次淡入，并默认选中“赛季结算”。

数据看板、平台配置与用户事务始终挂载在同一条三页轨道中。离开可视区域的页面使用 `inert` 隔离交互，页面内部的查询会话状态不会因切换而重建。

## 当前业务导航

| 分类 | 业务定位 | 当前状态 |
| --- | --- | --- |
| 赛季结算 | 查看当前结算赛季、正式参赛用户并发放积分 | 已接入真实接口 |
| 运动记录 | 使用自然语言查询业务数据并导出动态结果 | 已接入查询智能体接口 |
| 积分与兑换 | 使用 `rewards` 查询域检索积分与兑换相关数据 | 已接入查询智能体接口 |

点击分类时，左侧选中流光平滑移动到目标项，右侧内容容器保持稳定，不发生尺寸跳变。

赛季结算、运动记录和积分与兑换使用三个独立面板容器。非当前面板会被同时隐藏并设为不可交互，避免业务内容在切换后残留到其他分类。

> [!IMPORTANT]
> “赛季结算”以唯一 `status = 2` 的赛季为范围，不表示每上传一条运动记录就即时发放积分。

## 赛季结算

管理员进入“赛季结算”后，页面自动获取唯一结算中赛季，再按接口返回的 `season_user_ids` 批量加载正式参赛用户。参赛记录超过 1000 条时，前端按接口上限顺序分批查询。

当前结算赛季工具栏提供“待终审记录”按钮。按钮使用懒加载的 PixiJS 画布，在悬停或键盘聚焦时播放液态色块扩张与流动反馈。点击后通过结算专用接口一次获取当前赛季全部待终审凭证，并让赛季结算卡片翻到背面，展示与“今日待办”一致的终审工作区；返回时反向翻回结算列表。

“待终审记录”左侧提供红色“一键结算”高风险入口。弹窗明确说明确认后会拒绝全部未决凭证，并根据最终进度定分和发放积分；管理员必须逐字输入 `我确认结算{赛季名称}` 才能启用最终按钮。确认后通过 `POST /settlement/complete` 将整季收口交由一个后端事务完成，请求期间锁定弹窗和用户事务导航。成功后先展示自动拒绝、新定分与新发放汇总，关闭弹窗后退出当前结算态；失败时不自动重试。

终审记录通过 `season_user_id` 关联已经加载的结算用户资料和头像，通过 `project_id` 关联该用户的有效项目，不重复请求用户详情。接口虽然没有直接返回 `level_id`，但挑战等级名称受数据库唯一约束，页面会从完整等级目录恢复等级主键，再与 `project_id` 组合加载目标要求。凭证图片仍通过受保护图片中转接口按审核进度分批加载。

结算工作区的通过与拒绝使用 `POST /settlement/final-review`，不调用普通赛季终审入口。服务端成功后记录从当前队列移除，并同步响应中的项目完成进度；由于终审响应不返回 `final_points`，页面随后只刷新对应用户的结算详情，使自动定分结果及时回到结算列表。

列表展示：

- 用户名称与部门辅助信息。
- 用户在该赛季选择的统一挑战等级。
- 每一个已锁定运动项目的完成进度。
- 该用户本赛季的最终积分。
- 终审和积分发放状态。

结算数据加载完成后，列表记录按接口顺序从右侧逐条减速进入。入场延迟设置总上限，避免正式参赛人数较多时离屏记录长时间不可见；系统启用减少动态效果时直接展示全部记录。

状态展示遵循以下规则：

- `final_points = null`：显示“待终审”。
- `final_points != null` 且 `points_issued = false`：显示“发放积分”按钮。
- `points_issued = true`：显示“已发放”。

> [!IMPORTANT]
> 首次点击“发放积分”只进入 3 秒确认态，管理员再次点击同一用户的“确认发放”后才通过 `POST /settlement/issue-points` 提交。页面只在服务端确认积分流水与 `points_issued` 状态成功更新后切换为已发放，不执行乐观更新。

当当前结算赛季的全部用户均已发放后，页面显示“导出 Excel”入口。导出的 `.xlsx` 文件包含用户、部门、挑战等级、逐项运动进度、结算积分和积分状态；仍有待终审或待发放记录时不提供导出入口。

页面覆盖加载、无结算中赛季、多个结算中赛季、无人参赛、接口失败和手动刷新状态。没有结算中赛季时只展示工具栏圆形刷新图标，不在空状态内重复提供“重新获取”；其他加载异常仍保留就地重试。头像沿用管理端受保护图片中转，单张头像失败时保留姓名首字。

## 运动记录智能查询

审核员进入“运动记录”后，可以直接描述想查询的内容，例如：

- 查询本赛季所有待终审的运动记录。
- 查看跑步项目中被终审拒绝的记录。
- 按部门汇总本赛季运动记录审核情况。

后台结果通过 `headers` 明确返回字段键和展示名称，前端按 `headers[].key` 读取每行数据，并以 `headers[].label` 生成动态表头。因此明细查询和聚合查询可以使用不同列结构，不需要为每一种问题预先编写固定表格。查询任务由后端异步执行，前端通过 Bearer `fetch` 订阅 SSE，不把查询请求误认为同步结果。

结果行可以携带隐藏的 `image_url`。该字段不生成表头，存在时点击记录行可在独立查看器中展示凭证照片，长图仅在查看器内部滚动且纵向滚轮按帧限幅，避免图片高速跳跃；未携带时表格行没有照片点击态。

每次查询先通过 `POST /agent/queries` 创建后台任务，再使用带 Bearer Header 的 `fetch` 流式读取 SSE。空闲提示在创建开始后淡出，每个新事件从当前区域底部淡入，并由竖向节点链串联。收到确认或澄清事件时，交互框从底部升起；规划阶段的字段核对以“确认并继续”“修正查询”的确认选项出现，页面会提示管理员核对每行含义、展示字段和返回范围。选择修正后，后端会进入可自由输入的字段、布局或范围澄清，修正方案会再次等待字段核对。管理员提交选项或自由文本后通过回答接口继续工作流。输入区右侧开关拨回 `O` 会发送真实 `DELETE` 请求，服务端确认后才结束本地任务。

任务进入 `completed`、`abandoned`、`failed` 或 `cancelled` 后，页面通过 `/trace` 获取服务端终态轨迹并归档，同时继续在当前工作区保留这次查询。若结果阶段完成事件与最终查询完成事件携带相同摘要，前端合并这两个连续节点，只留下最终“查询完成”。完成态按同一 `query_id` 单独读取结果表格，并把表格直接追加在最后一个轨迹节点下方；当前结果使用深色、带向上阴影的抽屉造型从工作区底部升起，横向居中并保留适度留白，仅顶部保留圆角，底沿沉入容器。查询摘要由最后一个完成节点统一展示；当前查询的下载按钮位于该节点右侧，历史结果的字段筛选与下载控件仍悬浮在表格右上外缘，不重复显示标题和摘要。只有提交下一次有效查询时，上一轮轨迹和表格才整体淡出。头部左侧的“查询历史”入口以纯 CSS 打字机循环播放纸张、滑架和键盘动作，并打开最顶层任务中心：页面先请求后端当前进程仍保留的最多 100 个查询 ID，再以 4 路并发补齐状态并过滤非终态任务。该入口不再创建 Three.js Canvas 或 WebGL 上下文。左侧任务条目按顺序从左侧缓缓滑入；点击条目后才按需读取完整轨迹和完成态结果表格，右侧详情独立淡入。展开和收起完整轨迹时中间节点均从中心向两侧错峰淡入或淡出，每条节点的高度变化会逐帧推移下方表格。结果到达后可下载 Excel，文件不包含隐藏的凭证照片地址。

页面覆盖 `running`、`waiting_for_confirmation`、`waiting_for_clarification`、`completed`、`abandoned`、`failed` 与 `cancelled`。历史页不渲染等待输入、确认或终止控件，只以只读提问卡片、选项与操作员回答卡片回放既有 `interaction_requested`、`interaction_answered` 轨迹；普通进度仍采用时间线展示。SSE 意外中断时以最后事件序号自动续接，会话已过期时转为可理解的失败终态。

查询历史不再注入本地种子任务。缓存 ID、状态、轨迹或结果加载分别处理加载、空数据与失败状态；后端服务重启或 TTL 到期后，对应记录会自然从缓存 ID 列表消失。

> [!IMPORTANT]
> 前端只展示查询智能体返回的安全事件、轨迹与审计后表格，不接收 SQL、隐藏推理、模型原始响应或工具参数，也不会直接执行审核员输入的内容。

## 积分与兑换智能查询

管理员进入“积分与兑换”后，使用与运动记录一致的真实查询会话、SSE 进度、历史轨迹、动态表格和 Excel 导出交互，但创建请求会将 `domain_key` 设置为 `rewards`。当前后端对白名单和可查询字段的限制仍然有效。可尝试描述：

- 所有兑换明细。
- 待发放或已发放的兑换记录。
- 按商品汇总的兑换次数、积分和发放情况。

兑换明细不带图片元数据，表格行不可点击，也不创建图片查看器。运动与兑换查询由两个独立组件实例管理当前输入和运行状态；缓存 ID 接口返回所有业务域的任务，前端会按会话状态中的 `domain_key` 分别筛选 `sports` 与 `rewards` 历史。

> [!WARNING]
> 真实兑换结果字段完全以查询智能体的 `headers` 和 `rows` 为准，不能根据 `point_record` 猜测。

## 数据与接口边界

- 结算赛季来自 `GET /settlement/current`，用户详情来自 `POST /settlement/participants`，待终审查询与提交分别使用 `GET /settlement/pending-final-reviews` 和 `POST /settlement/final-review`，积分发放使用 `POST /settlement/issue-points`，整季收口使用无请求体的 `POST /settlement/complete`。
- 结算参与者详情按 `season_user_id → user_id` 写入工作台用户目录；后续终审记录使用该关系读取姓名、部门和头像地址，不重复请求用户详情。
- 赛季结算结果使用接口返回的 `final_points`，积分是否已计入流水使用 `points_issued`，前端不自行关联流水推导。
- 用户的赛季项目进度来自 `season_user_project.completion_progress`，挑战等级通过 `season_user.level_id` 关联 `project_level`。
- 运动记录以 `proof_record` 为结构参考，终审状态与进度影响遵循 `description/features/proof-review.md`。
- 智能查询使用 `/agent/queries` 创建任务、订阅 SSE、回答交互和取消；终态轨迹与结果表格按 `query_id` 分别读取。
- 运动记录照片使用 `proof_record.image_url`，但在动态表格与 Excel 中作为隐藏元数据处理。
- 商品信息可以关联 `product`，但当前没有独立兑换订单与发放状态数据库文档。
- 积分发放采用后端幂等结果；`issued_now = false` 仍表示已经发放成功，前端不得重复创建或推导积分流水。

> [!WARNING]
> 兑换记录所需的兑换时间、兑换积分快照、收件信息和发放状态均以后端查询域白名单与结果表头为准。

## 交互与无障碍

- 顶部模块与左侧分类均使用按钮语义。
- 当前分类通过 `aria-current="page"` 标识。
- 隐藏页面使用 `aria-hidden` 与 `inert`，避免键盘焦点进入不可见区域。
- 系统启用减少动态效果时，取消页面与导航的长位移动画。
